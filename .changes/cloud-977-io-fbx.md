# omuzaki-io-fbx: FBX import (binary 3000+ and ASCII)

- New crate `omuzaki-io-fbx` registers an importer for format `fbx` (import only). It reads the node hierarchy into an `IoScene` in canonical space: right-handed, +Y up, the model's front toward +Z, metres. Each node's local transform is expressed in those axes, so a turn about the file's up axis comes out as a turn about +Y (#977).
- `fbx.units_converted` and `fbx.axes_converted` (info) say when the file was not already in metres or right-handed Y-up.
- Limits: the input size, the node count, and ufbx's memory (1 GiB), allocation count and hierarchy depth (1024). A truncated file is `Malformed`; an OBJ or other non-FBX file is `Unsupported`.
- Meshes (triangulated, a primitive per material, glTF UVs, the front kept for a file of either handedness), skins (clusters as joints, `geometry_to_bone` as the inverse bind matrix, four weights), blend shapes (morph targets at full weight) and materials (ufbx's PBR reading, with base colour, emissive and normal textures, embedded or read beside the file as PNG or JPEG) are imported. A material an open surface uses (hair cards, a skirt) is double-sided, since FBX records no culling. Lights, cameras, curves and animation are reported as `fbx.content_dropped` (warning); `fbx.texture_dropped`, `fbx.unweighted_vertices`, `fbx.skins_dropped` and `fbx.inbetweens_dropped` say what else did not arrive. What ufbx repaired is reported as `fbx.repaired` (warning).
- An FBX character imports as an avatar (`SourceFormat::Fbx`): the humanoid is auto-mapped from its bone names. The kit's character written as FBX prepares as the same avatar as its VRM copy (silhouette IoU 0.99, the rest being the VRM's outline).
- The node cap and the input size set ufbx's memory and allocation ceilings (up to the fixed ones). `omuzaki-cli` links the importer, so `io.import` and `io.inspect` accept FBX.
