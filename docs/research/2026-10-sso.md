## 1. The three questions, one sentence each

1. **Can a desktop app complete OIDC with no Omuzaki-hosted server?** Yes: the app is a public client that sends the authorization code request with PKCE to a loopback redirect, exchanges the code at the IdP's token endpoint, and validates the ID token itself with the IdP's published keys (OIDC Core 1.0 §3.1.3.7, `verified`; loopback redirect per RFC 8252 §7.3: "The authorization server MUST allow any port to be specified at the time of the request for loopback IP redirect URIs", with `http://127.0.0.1:{port}/{path}` or `http://[::1]:{port}/{path}`; §8.3 accepts plain `http` on loopback because the request never leaves the device; §8.5 says a static secret in a distributed native app is not confidential, `verified`, https://www.rfc-editor.org/rfc/rfc8252 (checked 2026-10-13)).
2. **Can it complete SAML without one?** Not shown: the response is an HTTP POST from the browser to an assertion consumer URL registered at the IdP, and I found no primary text letting a loopback URL stand in for it (the loopback port exemption is an OAuth rule, RFC 8252 §7.3, with no SAML counterpart that I could read), so treat SAML as needing a bridge (team-run or Omuzaki-run) until an IdP's admin docs say otherwise (SAML 2.0 profiles §4.1: the `<Response>` is delivered through the HTTP POST or Artifact binding and the IdP "MUST ensure that any <AssertionConsumerServiceURL> ... are verified as belonging to the service provider", so a loopback ACS URL would have to be registered at the IdP; `verified`, https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf (checked 2026-10-13). No IdP documentation of a loopback ACS URL was found, so the conclusion stands).
3. **How do groups reach the app for Entra with more than 200 groups, and for Google Workspace?** Entra drops the `groups` claim past 200 (JWT) or 150 (SAML) and puts an overage marker in the token (`_claim_names`/`_claim_sources`, or `hasgroups` in the implicit flow), so the app must call Microsoft Graph `getMemberObjects` for the user (`verified`: `id-token-claims-reference.md`, "Groups overage claim"); Google Workspace puts no groups in the ID token and offers groups only through the Admin SDK Directory API with a domain-wide-delegated service account, which a desktop app cannot hold (`verified`: Google's ID-token claim list has no `groups` claim, https://developers.google.com/identity/openid-connect/openid-connect (checked 2026-10-13); Dex's Google connector page agrees).

**RUSTSEC-2023-0071 (Marvin attack) in `rsa`**: `verified` from `rustsec/advisory-db` (`crates/rsa/RUSTSEC-2023-0071.md`): "Due to a non-constant-time implementation, information about the private key is leaked through timing information which is observable over the network"; `patched = []`; still affected as of 2026-09-12 for 0.9.10 and 0.10.0-rc.18; workaround: "Local use on a non-compromised computer is fine". Our `deny.toml` has `ignore = []`, so adding `openidconnect` fails the advisories check until the maintainers accepts an ignore. My reading (not advice): an ID-token check uses only public-key verification, and the advisory is about private-key operations, so the exposure for a verifier looks absent; whether to add the ignore is a maintainer decision. The alternative is to hand-write the verifier on a different crypto crate (section 5).

**What a minimal ID-token check must do** (OIDC Core 1.0 §3.1.3.7, `verified`, from the xml2rfc source; the order here follows it):

1. Fetch the discovery document from the team's issuer URL and the key set from its `jwks_uri`; keys come only from the issuer.
2. `iss` must exactly match the issuer identifier.
3. `aud` must contain the app's `client_id`; reject if it lists audiences not trusted ("must be rejected ... if it contains additional audiences").
4. Verify the signature with the issuer's keys using the JWT `alg`; **algorithm allow-list**: the spec says the `alg` "SHOULD be the default of RS256 or the algorithm sent ... at Registration". Reject `none` and every HMAC alg (the spec's MAC path derives the key from the client secret, which a public client does not have; that rejection is a design choice of ours, not spec text).
5. `exp`: "the current time MUST be before" it. The spec text for the standard flow gives no leeway figure; the Self-Issued variant says "possibly allowing for some small leeway to account for clock skew". Choose a small bounded skew (for example 60 seconds, the `jsonwebtoken` default) and document it.
6. `nonce`: if one was sent, it MUST be present and equal; the app always sends one.
7. If `azp` is present, check it. If `acr`/`auth_time` were requested, check them.
8. **Refresh responses are validated differently** (OIDC Core 1.0 §12.2, `verified` from [the xml2rfc source](https://github.com/openid/connect/blob/master/openid-connect-core-1_0.xml), read 2026-10-13): the response "might not contain an id_token", so a missing one is not an error. If one is returned, its `iss`, `sub` and `aud` MUST equal those of the ID token from the original sign-in (this is the subject-continuity check), `iat` is the new issue time, and a present `auth_time` still gives the time of the original sign-in. Signature and `exp` are checked as above. Do not apply step 6 (nonce) unchanged: the refreshed token "SHOULD NOT have a nonce Claim", but "if it is present, its value MUST be the same as in the ID Token issued at the time of the original authentication", so check the nonce against the original only when one is present. Keep the original `iss`, `sub` and `aud` with the session (not the refresh token's secret) for this comparison. Refresh tokens live only in the keychain.

## 5. What needs a Omuzaki-hosted identity service, and what does not

| Needs no Omuzaki-hosted service | Needs one (or a team-run broker) |
|---|---|
| OIDC sign-in against the team's own IdP (Okta, Entra, Keycloak, Auth0 and Google via OIDC) | SAML-only IdPs (a SAML-to-OIDC bridge: Keycloak, which the team can run, or a Omuzaki-hosted one) |
| ID-token validation, session and role mapping from the `groups` claim | SCIM provisioning (an endpoint the IdP can reach) |
| Entra overage handling: the app calls Graph with the user's own token | Google Workspace group membership (a delegated service account is a server-side credential) |
| Device grant as a fallback | Central, tamper-resistant enforcement: a server must enforce roles for shared libraries (LB-07) and audit logs (VC-10); a client-side check can be edited by the user. Out of scope here. |

## 6. Recommendation

- VC-12 is only half hosted. Ship **generic OIDC as a public client in the app** (`oauth2` for code + PKCE + device; the ID-token check in our own small module or `openidconnect` after an decision on the `rsa` advisory), no Omuzaki server, one config per team: issuer URL, client ID, scopes, groups-claim name, group-to-role map.
- Implement the **Entra overage path** (Graph `getMemberObjects`) from the start; it is not an edge case for large tenants.
- **Google Workspace:** support sign-in and an email/domain allow-list; do not promise group mapping without a team-run component (a Keycloak in front, or Cloud Identity attributes the team maps into a claim; neither is verified here).
- **SAML and SCIM:** defer to the hosted-services work. A team-run Keycloak broker covers SAML with no Omuzaki-hosted service; a Omuzaki-hosted bridge is a maintainer decision.
- Rejected: `samael` in the desktop binary (C libraries, work-in-progress crate).
- Needs a maintainer decision: the `rsa` advisory ignore, adding CDLA-Permissive-2.0 (`webpki-roots`) to the licence policy, the offline-grace policy, and whether a hosted SAML bridge is offered.

## 7. Privacy under SE-04

- **Tokens never in logs, ops, MCP output or project files.** Access, refresh and ID tokens and the authorization code are secrets (settings.md, "Secret": the OS keychain only, never a file, log, op record or MCP output). The `oauth2` secret types redact in `Debug`; our wrapper must also keep them out of `tracing` fields and error text.
- **Only the team's own IdP is contacted.** The app talks to the configured issuer's discovery, authorization, token and JWKS endpoints. Entra's overage call goes to `graph.microsoft.com`, a second host of the same vendor, and so must be allowed explicitly by name and shown in the privacy panel. No third-party hosts, no telemetry, no analytics in the sign-in flow.
- **No identity data leaves the machine except to the IdP.** Groups and e-mail are not sent to Omuzaki. A hosted bridge (if ever built) would see them; that would need its own SE-04 entry.
- **Loopback listener hygiene** (reasoning from RFC 8252's purpose, not a quoted rule): bind `127.0.0.1` only, a random port, one request, then close; check `state`; the nonce and PKCE verifier stay in memory.
- **Offline grace:** a cached session works offline only for a bounded period the team sets, so a removed user loses access once the refresh fails (a Omuzaki choice, not a standard).
