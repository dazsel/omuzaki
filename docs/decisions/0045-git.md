# 0045: Git is the person's own `git` program, called as a process; text commits cleanly, binaries stay out, and committing and pushing are person-only (2026-10-13)

**Status:** proposed.
**Context:** VC-04; spec v3 §7, §29, §37, §40; ADR 0003 (assets outside git), ADR 0021 (journal, keeper,
`project.reload`), ADR 0025 (branches are not git branches). **Design:** `docs/design/git.md`.

## Context

ADR 0025 settled that Omuzaki branches are not git branches, `.omuzaki/` is never committed and a git commit can be
imported as a point. It left open how Omuzaki reaches git, what "commits cleanly" promises, how binaries travel, what the
commit view shows and which git operations an agent may touch.

## Decision

1. **Access: the person's own `git`, as a separate process** (`omuzaki-git`, native only; the web build answers
   `Unsupported`). Rejected: `gix` (Apache-2.0 OR MIT, but push and commit hooks are unfinished on its own roadmap) and
   libgit2 via `git2` (MIT OR Apache-2.0 crate over GPL-2.0-with-linking-exception libgit2; Omuzaki would handle
   credentials and miss the person's hooks and filters). Licence register verdict for git: `external`.
2. **Clean commits:** deterministic bytes, saves that never rewrite an unchanged file, one entity per file named by a
   stable id, canonical key order, a file's existing line ending kept (CRLF stays CRLF; new files LF), trees compared as
   parsed values. Omuzaki writes only `.omuzaki/.gitignore` (`*`) and a nested `takes/.gitignore`; it never edits the
   person's `.gitignore`, `.gitattributes` or git config; a `.gitattributes` (`text`, never `eol=lf`) is offered once.
   `merges.toml` and `assets.lock` are committed.
3. **Binaries never go through git.** `assets.lock` carries hashes; clones fetch bytes from the VC-09 second location.
   A missing blob is a placeholder naming its hash, never an error. LFS is not built.
4. **Commit view:** commits import lazily as `kind = "import"` points on a `git/<ref>` branch; changed units come from
   `history.diff`, thumbnails from `render.preview`, both cached by commit id under `.omuzaki/git/`, computed off the UI
   thread (target 400 ms per thumbnail).
5. **Ops:** `git.status`, `git.log`, `git.show` and `git.import_commit` need `read` and are open to agents;
   `git.commit`, `git.push` and `git.pull` are person-only (`OpError::person_only`). `git.push` needs `net` and
   `publish` (so VC-11 review applies) and runs the licence gate as advisory. `git.pull` is fast-forward only.
6. **External changes** go through `project.reload` as one undoable transaction, after the folder settles;
   files with git conflict markers are never parsed or overwritten.

## Consequences

- No git code is linked into Omuzaki; git must be installed for the feature, which Omuzaki detects and says.
- New API crates `omuzaki-git-api`, `omuzaki-git-mock` and the implementation `omuzaki-git`; the conformance suite runs
  `FakeGit` and real git over a local bare repository with the same cases.
- Register rows: git (external), git-lfs (not used), gix and git2/libgit2 (evaluated, not used).
- Revisit `gix` when push, hooks and filters are done; the `Git` trait makes that a drop-in.
