# 0043: Team roles narrow a person's grants; membership is a signed log; review needs N other people (2026-10-13)

**Status:** proposed (cloud lead to accept on the PR). **Context:** VC-10, VC-11,
VC-12, LB-07; spec v3 §6, §12, §28, §29, §37; ADR 0020 (agent sessions), ADR 0021 (the journal),
ADR 0042 (identity, in flight). Design: `docs/design/team.md` and `docs/design/team-review.md`.

## Context

VC-10 promises roles per project and per library, agents narrowed by their person's role, an audit log, and agency
accounts; VC-11 a reviewer's approval before `publish` or a `broadcast` grant. ADR 0020 left the seams: `Principals`
("VC-10 roles narrow it later"), `Need::Review`, `OpRecord.on_behalf_of` and `approval`. There is no server, and a
person with the project folder can edit any file.

## Decision

1. **Six fixed roles narrow `Grants::person()`.** `Role::grants()` is one table over every scope (`review` and
   `script` included; a later scope is owner and admin only until an ADR gives it a row); owner and admin hold every
   scope and differ in governance; a viewer holds `read` only. An agent's grants are its ceiling ∩ its person's
   `role.grants()`, so a viewer's agent ends with `read` only. No custom roles.
2. **`TeamPrincipals` is the `Principals` source** when a project has `team/`; without it the project is solo and the
   local person holds `Grants::person()`, as today. A person is a key through a `PersonDirectory` service; `Actor` is
   unchanged.
3. **Membership is an append-only log of signed statements** at `team/log/<seq>`, rooted in the owner key that each
   member pins on first open. Each entry is checked against the roster folded before it: admins sign changes to the
   four lower roles, owners sign everything. Invitations are signed files (invite, then the invitee's acceptance), so
   no server is needed. A bad signature, broken chain, failed invariant or changed root makes everyone read-only until
   a former owner or admin restores `team/` through History.
4. **`team.*` writes carry `read`, `person_only` and a role check**, never a new scope, so no grant can lend team
   management to an agent. Agents may read the roster.
5. **Review (VC-11):** under a policy, `publish` ops and `broadcast` grants queue `Need::Review` after the dry-run and
   its licence gate, for agents and people alike (a person's own request is marked `PendingApproval.own`). N distinct
   full keys of reviewer, admin or owner approve; never the requester, never an agent; one rejection ends it. Every
   approval is a signed `ApprovalStatement` over a request hash that carries a persistent `RequestId` and the preview
   digest, so it can't be replayed after a restart or stretched over changed content; approvals are stored with the
   approved op under `team/approvals/`, and a remote reviewer's statement is imported by a person.
6. **Audit:** membership facts live in the signed log (shared); session, grant, approval and publish facts in the
   journal's skippable `audit` record (kind 11, per machine), copied into `.omuzaki/audit/` before the archive is
   pruned; `team.audit` merges them for owners and admins, and an export is signed.
7. **Agencies** are a per-user registry of clients, each with its own key, libraries and credentials; switching swaps
   all of them, and nothing crosses.
8. **The client enforces everything for free.** Hosted pieces (team store, review hosting, relay, identity service)
   are a maintainer decision.

## Consequences

- Roles are enforced for agents and for the person's own tools, and verifiable on every signed artifact; they are not
  a lock on files, and the Team panel says so in one sentence.
- `omuzaki-ops-api` gains `ReviewPolicies`, `ReviewRequirement`, `ApprovalRef.also`, `PendingApproval.own` with
  `SessionId::NONE`, `Decision::ApproveSigned` and `ErrorDetail::NotEligible`, all additive and folded into with
  the `review` scope, so the hub crate changes once in Phase 5.
- Roster forks are ordinary merge conflicts on one file; nobody folds a forked log.
- Session facts are per machine; anything a teammate must check is signed and in the document.
- Agency clients each use an identity slot (ADR 0042 D2), selected through `identity.use`; the team root pin is a
  per-user team record, not a `TrustStore` entry.
- Signatures use identity's `Signed<T>` envelope (ADR 0042). The roster also carries the team's licence and the
  library policy that shared sources (the shared-library-sources design, planned) enforce. Comments (the comments design) call `Role::can_moderate()` and feed
  the `no_open_threads` policy.
