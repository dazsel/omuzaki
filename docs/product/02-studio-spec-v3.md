# Part I: What and why

## 1. The product in one page


**Omuzaki** is one application where a person (or an AI agent working for them) can:
1. **Create** a character: from an idea, a sketch, a character sheet or an existing model, to a finished, rigged and expressive character.
2. **Perform** it live: from a webcam, an iPhone, mocap gear, a voice, or an AI performer, into any streaming setup.
3. **Reuse** it everywhere: games (VRM/glTF/Unity/Godot/VRChat), rendered shorts and music videos, emotes, stickers, thumbnails and sprites.

**What makes it different:**

- **AI-native, not AI-bolted-on.** Every action in the app is a typed operation. The UI, the MCP server, the CLI, scripts and plugins all call the same operations. Claude Code, Codex or any MCP client can do anything a person can, and the person can watch it happen live (the Build Theatre, §13) and approve, steer or undo it.
- **Characters are generated by code, not hand-sculpted.** A character is a set of parametric parts on a standard skeleton, with a procedurally painted face (decision 0002). So every character gets the full 52-control "perfect sync" expression set, physics, LODs and exports automatically. Today that's weeks of paid rigging per model.
- **One character, every output.** The same project drives the stream, the game export and the offline renders.
- **Fast and light.** Native Rust on the GPU. It must run beside a game on a mid-range laptop without anyone noticing (§10).
- **Free where it matters.** Full performance fidelity, all inputs, all outputs and the character creator are free. Basic quality is never paywalled (§37).

## 4. Principles

1. **One operation layer.** UI, agents, scripts and plugins are peers over the same typed ops. No back doors and no UI-only features.
2. **Show, don't just tell.** Every change an agent makes produces a visible result (render, diff, metric) before it's committed. People approve outcomes, not instructions.
3. **Measure, don't eyeball.** Likeness, liveliness, readability and performance are numbers with gates. Agents must check them (§15).
4. **Deterministic by default.** Same project + same seed + same inputs = the same frames. That's what makes renders reviewable, tests possible and agents trustworthy.
5. **Text-first project format.** Diffable, mergeable, agent-editable. Binaries live in a content-addressed store with provenance.
6. **Licence-clean by construction.** Every asset and model carries provenance. A licence gate blocks non-commercial material from shipping (§40).
7. **Real-time path stays local.** No cloud in the live loop. AI authoring can use the cloud when the user opts in.
8. **Graceful AI, solid core.** AI features may fail softly; the deterministic editor and runtime may not.
9. **Compatible first, then better.** Import and export the formats people already have (VRM, glTF, VMC, OBS), then exceed them.
10. **Small, fast, quiet.** Budgets are part of the spec, and a feature that blows the budget isn't done.

**Three planes:**
- **Real-time plane:** tracking → retarget → life layer → physics → render → output. Fixed budgets, no allocation in the hot loop, no network.
- **Authoring plane:** edits, generation, import/export, renders. Transactional, reproducible and undoable.
- **Model plane:** local inference (ort, candle) and opt-in remote providers, behind versioned interfaces with licence metadata.

## 6. The operation layer (the heart of the system)

Every state change in Omuzaki is an **op**: a typed, serialisable, schema-described command.

```rust
#[derive(Op, Serialize, Deserialize, JsonSchema)]
#[op(name = "face.set_profile", scope = "edit:character", undo = "auto")]
/// Set the head's face-shape profile (outline, chin, feature layout).
pub struct SetFaceProfile { pub character: CharId, pub profile: FaceProfileId, pub blend: f32 }
```

**Properties every op has:**

| Property | Meaning |
|---|---|
| **Typed schema** | JSON Schema generated from the Rust type (schemars). It's the MCP tool schema, the CLI flag set, the script binding and the docs, all from one source. |
| **Validation** | Range and reference checks before anything changes; errors are structured and actionable. |
| **Dry-run** | Returns the patch (document diff) and, on request, a preview render, without applying it. |
| **Transaction** | Ops group into atomic transactions with a label ("make the face more oval"). A transaction is one undo step. |
| **Undo/redo** | Automatic inverse patches; explicit inverse for ops with external effects. |
| **Provenance** | Each applied op is logged with its actor (person, agent id, plugin), cause (prompt, chat message, rule), parent transaction and timestamp. |
| **Permissions** | Each actor holds capability scopes (below). An op outside the actor's scope is refused, or queued for approval. |
| **Events** | `op.applied`, `render.ready`, `metric.updated` and so on stream to subscribers: UI, Build Theatre, MCP notifications. |
| **Cost hints** | Expected time, GPU memory and money (for cloud connectors), shown before anything expensive runs. |

**Queries** are read-only ops (`project.get`, `character.describe`, `render.preview`, `measure.*`). They never need approval.

**Jobs** are long-running ops (renders, generation, training, batch export). They run in a job manager with progress, cancellation, resource caps (CPU/GPU/memory/process count) and timeouts. A runaway job can't take the machine down (lesson: the WSL hang).

**Capability scopes:**

> Amended 2026-10-12 (ADR 0027): `edit:show` (automation graphs and other show setup), `input` and `process` are added.

- `read`
- `edit:character`, `edit:scene`, `edit:show`, `edit:library`, `edit:settings` (the person's settings, profiles and session list; never project data)
- `perform` (drive the avatar live)
- `broadcast` (go live, switch scenes)
- `publish` (export or upload outside the machine)
- `spend` (paid connectors, with a budget)
- `net` (network access)
- `fs:<path>` (file access outside the project)
- `native` (load native code)
- `process` (start other programs, or see whether named programs are running)
- `input` (capture OS keyboard, mouse and gamepad input)

Defaults: people get everything; agents get `read` + `edit:*` (including `edit:settings`) + `render`; `broadcast`, `publish` and `spend` need a per-session grant.

**One registry, five surfaces.** The op registry generates:
1. MCP tools (§11)
2. CLI subcommands (`omuzaki face set-profile --character mira --profile default`)
3. script and plugin bindings (§30)
4. the UI command palette, with every action searchable by name
5. reference docs

Adding a feature means adding ops. The UI is one client of them.

## 7. Project and data model

**Project layout:** a directory, git-friendly and mergeable.

```
my-show.omuzaki/
  project.toml               name, schema version, default character, default scene, default show, settings
  characters/<id>/
    character.toml           parts list + parameters (body, head profile, face, hair, outfit, accessories)
    face.toml                face profile, feature layout, expression set, style params
    rig.toml                 template rig ref, fit params, spring chains, colliders
    look.toml                materials, palette, outline, lighting response
    variants/<name>.toml     per-use overrides (game, close-up, emote, VRChat Quest)
  scenes/<id>/
    scene.toml               name, subject, opening camera, backdrop, ground, post (docs/design/scenes.md, ADR 0024)
    lighting.toml            the light rig as values: ambient, lights, exposure, fog, environment
    cameras/<id>.toml        framing presets (face, bust, full) or free cameras
    cast/<member>.toml       which character stands where
    props/<id>.toml          props
    applied/<app>.toml       library items applied to the scene (ADR 0019)
  performances/<id>/
    score.toml               authored performance (keys per channel), like a reference-clip score
    takes/<n>.track          recorded inputs (52 controls + head + hands + audio ref), compressed
  shows/<id>/
    show.toml                name, seed, variable declarations, groups (docs/design/automation.md, ADR 0027)
    automations/<graph>/     graph.toml (name, enabled, group) and nodes/<node>.toml (kind, params, wires, constants)
    applied/<app>.toml       library templates applied to the show (ADR 0019)
                             (outputs, hotkeys and overlays add their own keys with their designs)
  (no library.lock file)     each applied item's record pins id@version + hash in the tree: characters/<id>/applied/ (ADR 0019)
  tray/<candidate>.toml      connector outputs waiting for, or decided by, a person: request, provenance copy, state (§14, ADR 0030)
  assets.lock                content hashes → store, with provenance
  .omuzaki/                    cache, op log, thumbnails, automation variable values (not committed)
```

**Rules:**
- One entity per file, stable key ordering, no binaries in text. Merges are clean, and agents can read and edit files directly when needed (ops remain the preferred path).
- **Schema versioning with migrations.** Old projects always open.
- **Content-addressed store** (BLAKE3) for binaries: images, meshes, audio, model weights, renders. Local by default; optional sync to the user's cloud bucket. Dedup is automatic.
- **Provenance record per asset:**
  - source: tool, model + version, prompt, seed, input asset hashes
  - author
  - licence (SPDX id or a custom record)
  - consent flags (for likeness or voice)
  - commercial status: ok / no / unknown

  The **licence gate** blocks `publish` of anything `no` or `unknown`, with a clear explanation.
- **Live collaboration** (phase 5): the project document mirrors into a CRDT (loro, with a movable tree for the scene graph), synced over QUIC (iroh). Ops stay the unit of change; the CRDT carries them.

## 8. Runtime model

- **ECS-style data** for the live scene: characters, props, cameras and lights are entities. Systems run in a fixed order each frame:
  `input → track → retarget → life → anim blend → IK → physics (spring bones, hair, cloth) → face paint → render → outputs`.
- **Frame budget scheduler:** each system has a ms budget and reports usage. Over budget → degrade gracefully (fewer physics sub-steps, lower face atlas resolution, skipped shadow updates) and tell the user, rather than dropping frames.
- **Determinism:** fixed-step simulation (physics at 120 Hz sub-steps); seeded RNG per system; recorded inputs replay bit-identically for renders and tests.
- **Threads:** capture/tracking on its own thread(s) with lock-free hand-off (newest frame wins, never queue). Render on the main/GPU thread. Jobs on a pool. Audio on a real-time thread.

**Tech choices** (from `2026-10-rust-stack.md`):
- wgpu with a custom toon renderer (the Rerun pattern), not a full engine. Bevy changes too fast and has no editor.
- egui + egui_dock/egui_tiles + egui-snarl for the editor UI.
- rmcp for MCP; ort (ONNX Runtime: CUDA/DirectML/CoreML/WebGPU) for inference; Whisper and Silero VAD for speech (not sherpa-onnx: its Rust crate links GPL espeak-ng, §40).
- loro + iroh for collaboration; wasmtime (or extism) for plugins.
- LGPL FFmpeg (shared libraries, hardware encoders) for encoding; str0m for WHIP; native shims for virtual cameras.

Everything is pinned to one wgpu version, upgraded deliberately each quarter.

**For parallel development (§39),** every subsystem above is split into a small `*-api` crate (contracts), a `*-mock` crate and one or more implementation crates. Implementations depend only on API crates.

**The budget scene and how every row is read.**
- **Scene.** One seed-library character in its default style with hair and outfit; the camera framed on the face and upper body; 1920 × 1080 output at 30 fps; the live preset (LK-05, render scale 1.0, 4 samples); a recorded tracker replay driving it; one output (Spout, NDI or virtual camera) and no encoding in the app; the editor UI closed unless a row says otherwise. It is a fixture owned by the budget harness and holds no private test material.
- **Paced, warm, long enough.** The scene runs paced at 30 fps, as in use, because a GPU in a tight loop sits at higher clocks and reads faster than it will on a stream. Each run warms up for at least 20 s, then records at least 3,000 frames; a 400-frame run read 8 to 10% higher than a 60,000-frame run on `Dev` (research `2026-10-reference-machine-definition.md` section 5).
- **Clocks.** GPU time comes from GPU timestamp queries and CPU time from the OS's CPU-time counters, never from a stopwatch around the work, so a loaded CI machine cannot move them. `p95` is the budget percentile for every per-frame row; the p50, p99 and maximum are reported beside it.
- **Units.** MB and GB mean MiB and GiB, as Task Manager shows them. The installer is the exception: decimal MB (150 MB is 150,000,000 bytes), the stricter reading.

**Definitions, by key.**
- `cpu.total`: CPU time (user plus kernel, every thread) of the Omuzaki process and every process it starts, divided by 8 × elapsed time. 3% of 8 cores is 0.24 core-seconds per second, which is **8 ms of CPU per frame at 30 fps**. **The tracker is inside it.** Two configurations are measured and both must pass: tracking from a phone (receive and decode only), and from a webcam on the tracker's default execution path for the tier. A webcam tracker that runs on the CPU at its full 5 ms uses 62.5% of the 8 ms and leaves 3 ms for everything else. A 60 fps camera doubles the tracker's cost and is outside this row. The basis is 8 cores whatever the machine has (`F` has 4).
  `cpu.total` is read with **captions off**: the speech host only listens (`asr.listen` is inside it). A second budget scene turns captions on and is judged on `asr.live` on top of the scene, not inside the 3 %.
- `asr.listen`, `asr.live`, `asr.final`: ASR is **demand-driven**. The speech host runs Whisper only while a consumer (captions, the conversation loop, the AI performer) holds a transcript claim; with none it only listens, and the listening cost is the baseline (`asr.listen`). `asr.live` is the feature cost of transcribing on top of it. `asr.final` counts from the last spoken sound and includes the end-of-speech hangover (default 600 ms on the CPU recogniser, shorter where calls are cheap). **CPU fallback** (no usable GPU; `tiny.en` or `base.en`, VAD-gated, 600 ms hangover): it cannot meet `asr.live` and has no budget; the UI shows that captions cost CPU on that machine. Measured on `Dev` under load (unscaled, 8-core basis, 84 % talk ratio, best of two): `tiny.en` 4.4 % CPU, final text p95 1.4 to 1.8 s; `base.en` 6.7 % CPU, p95 1.7 to 1.8 s; one thread cannot keep up with `base.en` (research `2026-10-speech-host-cpu.md`).
- `gpu.frame`: the sum of the GPU time of every pass of a frame **except face paint and particles** (the `PaintTextures` and `Particles` passes, each its own row below), p95 over the frames. `gpu.frame.quality` is the same with the quality preset.
- `gpu.face_paint`: the GPU time of the face-paint pass over the frames that repaint the face. It is **on top of** `gpu.frame`, not inside it (render API decision Q6). A frame that repaints the face may therefore take up to 1.5 + 0.5 = 2.0 ms (4.5 ms in quality mode); that total is reported as `gpu.frame_with_face` and is not gated on its own. **Where it is measured:** a full face does not fit 0.5 ms (about 0.8 ms GPU at 300 to 900 commands, 1548 x 1107, on the 4090), so the painter repaints by section: each section keeps a cached layer and a frame redraws only the sections whose inputs changed. lavapipe is never a timing machine for the face: it checks **correctness at probe size** only (PSNR against the CPU rasteriser). The timing gate runs on a real-GPU job; until that job exists, every PR that touches the face painter attaches 4090 numbers taken natively on Windows (Vulkan and DX12).
- `track.face`: wall time from a camera frame handed to the tracker to its channel values published, on the tracker's own thread, at a 30 fps camera. The report names the device that ran it (CPU, iGPU, NPU). Its CPU time is already counted in `cpu.total`.
- `physics.step`: the physics step of one frame, all sub-steps (four at 120 Hz in a 30 fps frame), over the replay. The criterion benches of the same code run on one E-core as regression detectors; they do not replace this row.
- `gpu.particles`: the GPU time of the `Particles` pass (ADR 0028) in the **particle budget scene**: the budget scene plus 5,000 live particles held steady (snow keeping 3,500 alive and a confetti fountain of 300 per second with a 5 s lifetime), at 1080p30 on the live preset. It is **on top of** `gpu.frame`, like face paint: `gpu.frame` does not include the `Particles` pass, so the budget scene (which has no particles) reads the same. The stage caps live particles at 5,000 slots in performance mode, and the §8 scheduler lowers the particle density first when this row or the frame is over budget. The number is a design estimate until the measurement task reports it on `Dev`, converted by the rules below.
- `ram.runtime`: **private working set** (`PrivateWorkingSetSize`; the Memory column of Task Manager), the Omuzaki process and its children summed, in performance mode (avatar live with tracking and one output, no editor UI). It is taken on **each hardware graphics backend** the app can choose on that OS (Windows: Vulkan and DX12), never on a software adapter (WARP, lavapipe), and the largest value counts. The report also holds working set, commit and a baseline with an empty device, so the driver's share is visible. Commit is not the counter: the renderer alone already peaks at 476 MB of commit on DX12 on `Dev`. Memory on the GPU (dedicated and shared) is reported as `gpu.mem` and has no budget yet. On macOS the counter is `phys_footprint` and on Linux the proportional set size (PSS), gated once such a machine exists.
- `ram.editor`: the same counter with the editor UI shown, the budget project open (200 files, the size the `omuzaki-doc` open bench uses) and the viewport live.
- `latency.desktop`, `latency.laptop`: camera exposure to photon from the QG-02 rig, per input path and output; the camera, display refresh rate and output path are recorded. Real hardware only: this row is never scaled.
- `startup.live`: process start to the first presented frame of a performing avatar, with device, pipelines, model and first frame timed separately. Two cases, both gated: **warm** (a second launch right after the first) and **cold** (the first launch after a reboot, so the OS file cache is empty while our pipeline cache and the driver's shader cache are kept). The very first launch after an install, with no caches, is reported and not gated: shader compilation belongs to the driver. Provisional gate until `R` is measured: ≤ 1.0 s on `Dev`, half the budget, to leave room for slower drivers.
- `floor.dropped_frames`: on `F`, the budget scene for 5 minutes at 30 fps with the §8 scheduler on. Every step the scheduler takes down is logged and shown to the user.
- `voice.fx`, `voice.fx.pitch`, `voice.fx.cpu`: the BR-24 chain at 48 kHz (`voice.fx.cpu` with every effect on, pitch and formant included) and the audio device's block size (the gate uses 256 samples, 5.3 ms). Latency is the chain's own look-ahead plus buffering, never the device's; the device's round trip is reported beside it. The chain runs whether or not the budget scene uses it, so its CPU is reported on top of `cpu.total`, not inside it. A user's voice-conversion model (ML-14) has no budget: its latency is measured, shown and reported as `voice.vc`, never gated.

**Numbers from other hardware.** Every number in a report carries one class:

| Class | Taken | Judged |
|---|---|---|
| `measured` | on the tier it is claimed for | against the budget directly |
| `scaled` | on another machine, converted by a rule below | GPU: the central estimate must be ≤ the budget (a hard fail) and a pessimistic estimate over it is a warning. CPU and memory: the rule is a bound, so the number is compared with the budget directly. Printed as "estimate" until calibrated |
| `relative` | a PR against main on the same machine, alternating runs in one session | any budgeted metric more than 10% worse fails (§34) |
| `reported` | on any other machine (a cloud build machine, a contributor's laptop, hosted CI) | printed with the machine's name; never gates, never quoted as a tier's number |

Conversion rules:
- **GPU** (`gpu.*`): on `Dev` (Windows build, Vulkan and DX12), measure the per-pass GPU time at 720p, 1080p, 1440p and 4K and fit `fixed + per-pixel × megapixels`. Estimate a tier three ways: optimistic = fixed × 1.5 + pixel part × memory-bandwidth ratio; central = fixed × 3 + pixel part × 3DMark Time Spy graphics ratio; pessimistic = the whole frame × the Time Spy ratio. Time Spy ratios of the 4090 to each tier: `R` 15.8, `F` 23.4, `U` 12.1. The constants and their sources live in `reference.toml` (below).
- **CPU** (`cpu.total`, `physics.step`, `track.face` on the CPU): run on `Dev` pinned to its E-cores (a Windows affinity mask; Linux `taskset` does not separate core types). An E-core measured 1.49x, 1.96x and 1.74x slower than a P-core on integer, FMA and L2-memory kernels, and `R`'s core is 1.43x slower than a P-core (the E-cores are 1.04 to 1.37 times slower than `R`), so a pass on the E-cores is a pass on `R`. No other conversion is applied; the number is printed as `scaled`.
- **Memory:** no conversion; the counters do not scale with the CPU or GPU, only with the driver, which is why the backend is part of the row. The driver share is confirmed at the first calibration on `R`.
- **Startup:** the provisional `Dev` gate above, until a calibration run records the real ratio.
- **Latency and installer size:** never converted.

**Calibration.** One run of the budget harness on a real device of a tier is recorded in `crates/omuzaki-test/src/budget/reference.toml` as a `[[calibration]]` entry: date, tier, device, OS build, driver, backend, and the measured and predicted time per pass with their ratio. The same file holds every conversion constant with its source. A metric stays an estimate until its tier has an entry for it. An entry may change a constant and never a budget: changing a budget is a spec change. Who provides the first real device is a maintainer decision.

## 13. The Build Theatre: watch it being built

> Restored/added 2026-10-11 (decision: no later tier): TH-01 to TH-12 give every view and control in this section a feature ID.

A dedicated workspace (and a pop-out window) that turns agent work into a watchable, steerable show.

**Views:**
1. **Live viewport:** the character as it changes, with a soft highlight on the part being edited and a caption of the current op ("Hair: adding fringe, 9 locks").
2. **Timeline of steps:** each transaction is a card with its label, actor, cause (the prompt line it came from), before/after thumbnails, metric deltas (likeness ↑, budget used) and duration. Cards nest under plan items.
3. **Plan board:** the agent's plan as checklist items. Each item links to its transactions, and each shows status: planned / running / needs review / done / failed gate.
4. **Compare strip:** reference vs current vs previous at a matched camera. It updates every step, the way a face is matched against a character sheet and reference frames.
5. **Branches:** agents can explore variants in parallel ("oval face A/B/C"). The theatre shows them side by side; the person picks, and the others are kept as branches.

**Controls:**
- **Pause, step, resume:** pause after every transaction, after each plan item, or only at gates.
- **Approve or reject** with a comment; the comment is fed back to the agent.
- **Rewind:** jump to any card; undo back to it, or branch from it.
- **"Explain this":** the agent's rationale for a step, in plain words.
- **Draw to direct:** circle a region in the viewport and type "make this rounder". The note becomes an op target with a screenshot and coordinates.
- **Budget meter:** time, tokens and connector credits spent, with stop limits.

**Recording:** every build can be exported as a time-lapse video (renders per step, with captions), shareable as a "making of" (also good marketing content).

**Replay:** the whole build is an op log, so it replays on another machine and can be re-run with different choices (seeds, references, profiles).

## 14. Connectors for artists' AI tools

## 15. Verification loops: what agents must check

> Restored/added 2026-10-11 (decision: no later tier): VF-01 to VF-09 give every check below, and the `measure.*` / `render.*` tools behind it, a feature ID.

Agents (and people) don't call work done until its gates pass. Each op family has default checks:

| Change | Check | Tool |
|---|---|---|
| Shape or likeness edits | side-by-side vs reference at matched camera; outline curve and feature spacing (normalised by eye distance) within tolerance | `render.compare`, `measure.face_outline`, `measure.feature_spacing`, `measure.likeness` |
| Expression or face channels | channel sweep contact sheet (each control at 0/1); every control visibly moves, in the right direction | `face.channel.sweep` |
| Anything touching shared parts | golden-render regression on other variants (game face pixel-identical unless intended) | `render.golden.check` |
| Rig / physics | stress-test poses (arms up, crossed, sitting, head turns of ±60°); interpenetration and clipping report (chin vs collar, hair through face) | `rig.stress_test` |
| Performance | liveliness metrics: frame-to-frame change, blink rate, saccades, longest frozen window, vs reference or human baseline | `measure.liveliness` |
| Readability | emote sizes (112/56/28 px), silhouette at 64 px, palette value contrast, colour-blind simulation | `measure.readability`, `measure.silhouette`, `measure.palette_contrast` |
| Runtime cost | frame budget per system, triangle and material counts, VRChat performance rank | `measure.perf` |
| Licence | provenance complete; no `no`/`unknown` commercial status in shippable assets | licence gate |

A failed gate becomes a Build Theatre card with the evidence image, so the fix is obvious (TH-11).

4. **Score drafter** (ML-10): clip → performance score (keys per channel). Vision LLM plus the trackers, refined by a small model.
5. **Readability and likeness critics** (ML-11): small scorers used in the gates.

**Every model:** versioned, behind an interface, with an eval suite, a licence record, and fallback when it's missing.

# Part V: Craft

## 32. How to make better characters

Good characters follow rules that can be **checked**. The studio teaches them through the **character report card** (CB-92): each rule has a check and a fix.

| Rule | Why | Check (automated) | Fix suggestions |
|---|---|---|---|
| **Readable silhouette** | recognisable at a glance and at thumbnail size | black silhouette at 64 px against 20 other characters; distinctiveness score | exaggerate hair shape, add an asymmetric accessory, a signature shape (ahoge, hat, wings) |
| **Face reads at emote size** | Twitch emotes are 28 px | expression set rendered at 28/56/112 px; similarity between expressions; contrast of eyes and mouth vs skin | thicker lash line, bigger mouth shapes for emotes, stronger blush, emote-specific line weight |
| **Value contrast** | colour without value contrast reads as mush on stream | value separation between hair / skin / outfit / background; colour-blind simulation | darken one of each adjacent pair; palette suggestions |
| **Expression range** | soul needs range | channel sweep + expression range test; no dead controls; at least 6 clearly distinct emotions | tune per-channel gains; add anime extras; widen mouth shapes |
| **Close-up proportions** | a chibi face read up close needs a longer lower face, visible neck, bangs | likeness and feature-spacing vs a close-up target; neck clearance | close-up variant (CB-13) |
| **Eyes are the soul** | most of the life is in the eyes | highlight count and motion; iris gradient; lash weight; eye white share; gaze range | sparkle presets, moving reflections, lower-lash options |
| **Hair frames the face** | the hairline shapes the perceived face | bangs coverage of the forehead; framing locks vs face edge; brows still visible | bangs presets; brow-over-hair |
| **Motion personality** | consistent "acting" makes a character | life-layer preset fits the persona (energetic vs calm); blink rate, head motion amplitude | pick or tune a personality preset |
| **Consistency across views** | turnarounds must agree | front / side / back renders vs sheet views; likeness per view | fix per-view mismatches |
| **One signature detail** | memorability | at least one unique motif (palette, accessory, hairstyle element) | suggestions from the brief |
| **Budget fit** | must run beside games and in VRChat | perf budget, VRChat rank | decimate hair, merge materials |

## 33. Lessons from the prototype (lessons → features)

Building a character by hand in the JS prototype showed exactly which tools were missing. Each became a feature above:

| # | What happened | Missing tool | Feature |
|---|---|---|---|
| 1 | The face was matched to the sheet by eye, back and forth, over many renders | overlay the sheet on the model at a matched camera, with a difference heatmap | CB-25, `render.compare` |
| 2 | The "cute" face came out wider than the intended oval; it was fixed only after **measuring** the reference outline | measure outlines and feature spacing from any image or video, normalised by eye distance | CO-06, `measure.face_outline` |
| 3 | The same character needed a sheet-faithful game face and a close-up face matched to a close-up reference | per-use variants switched by shot distance | CB-13, SH-10 |
| 4 | Face edits needed proof that they did not change the game face | golden-render pixel diff as a one-click gate | `render.golden.check` |
| 5 | 24 new face controls were checked one by one | channel-sweep contact sheet | `face.channel.sweep`, FE-04 |
| 6 | A 20 s clip was transcribed into a 93-key score by watching it at 12 fps | clip → score drafting | SH-04, model 4 |
| 7 | Frame-exact renders were needed, with continuous hair physics | deterministic offline renderer with recorded inputs | SH-01, SH-05 |
| 8 | "Soul" was hard to discuss until measured (frame change, blink rate, frozen windows) | liveliness metrics | `measure.liveliness`, PF-26 |
| 9 | New bangs hid the brows; nothing flagged it | layering rules + expression range test catching invisible controls | CB-21, FE-04 |
| 10 | Chin sank into the collar; hair swung through the face on big turns | stress test with clipping reports | RG-07, CB-42 |
| 11 | Six agents were coordinated with file fences by hand | Build Theatre with roles, fences, approvals | §12, §13 |
| 12 | Licences were researched by hand for every model and dataset | provenance + licence gate | §7 |
| 13 | A runaway test hung the whole machine | job manager with resource caps and timeouts | §6 jobs |
| 14 | Tracker signs (roll direction, matrix layout) were easy to get wrong | built-in calibration and axis checks with visual confirmation | PF-20, PF-27 |
| 15 | Reviewing work meant assembling contact sheets with scripts | contact sheets and side-by-sides as built-in render ops | `render.contact_sheet`, `render.compare` |

## 36. Risks and mitigations

> Restored/added 2026-10-11 (decision: no later tier): the scope risk no longer relies on cutting P0; the egui and Live2D rows point at their exit criteria and decision.

| Risk | Mitigation |
|---|---|
| **Rust ecosystem churn** (wgpu, egui and rmcp ship breaking releases often; ort is still an RC) | pin versions; one upgrade window per quarter; thin adapter layers around each |
| **Avatar format gaps** (young VRM 1.0 / MToon / spring-bone crates) | own the VRM I/O and spring bones in `omuzaki-io` / `omuzaki-rig`, tested against UniVRM-produced files |
| **OS glue** (virtual cameras, Spout, NDI, macOS camera extension in Swift) | small native shims per OS in `omuzaki-stream`, built early (phase 0/2), tested on real machines |
| **Pro editor UI in Rust** (docking, timeline, node graphs, IME, accessibility) | egui + egui_dock/tiles + egui-snarl; build a timeline widget ourselves; AccessKit; budget design time; the polish bar, its exit criteria and the fallback are written in open question 1 and checked by QG-12 |
| **Licensing** (FFmpeg LGPL, NDI attribution, model weights, ICT scan consent, Live2D) | licence policy and register (§40); cargo-deny on every PR; provenance gate; legal review before launch; Live2D Cubism is not used (decision 0010); LGPL FFmpeg as shared libraries |
| **Style ceiling** (a code-drawn face must reach pro Live2D/3D polish) | a dedicated art-direction track; reference-match gates; library curated by artists; the report card |
| **AI performer quality** (big moves need intent, not noise) | intent planner + voice/intent → face model trained on consented takes |
| **Scope** | everything ships (decision 2026-10-11), so scope is managed by build order, not by cutting: P0 first, then P1, then P2; phases end with milestones that a real streamer uses, and a phase is done only when every feature in it is closed |

# Part VII: Built for massive parallel development

## 39. Architecture and workflow for many parallel PRs

> Scope: epics cover §12–§16 and §34 as well as §17–§31, and a phase is done only when every feature in it is closed.

**Goal.** Dozens of pull requests open at once, by people or AI agents, each small, independent and mergeable within hours, with nothing sacrificed in quality, speed or design. The architecture makes parallel work the default: **no shared hot files, stable contracts, everything testable offline.**

### 39.1 Architecture rules

| # | Rule | Why it enables parallel work |
|---|---|---|
| 1 | **Contract-first crates.** Every subsystem has a small `*-api` crate (traits, data types, op and event types) that changes rarely and needs maintainer approval. Implementations live in separate crates that depend only on APIs. Example: `omuzaki-track-api` (Tracker trait, frame and blendshape types), with `omuzaki-track-mediapipe`, `omuzaki-track-iphone` and `omuzaki-track-vmc` as siblings | three contributors build three trackers at once without touching the same files |
| 2 | **No central registries in source.** Ops, inputs, exporters, gates, automation nodes, library items and connectors **register themselves** (distributed registration via `inventory`/`linkme`). Adding an op = adding one file; nothing edits a central enum, match or list | no merge conflicts on "the big list" |
| 3 | **Vertical slices.** A feature lives in one folder: op structs, handler, tests, fixtures, golden images and docs (`crates/omuzaki-face/src/ops/set_profile/…`) | a PR touches one folder |
| 4 | **Generated artefacts aren't committed.** MCP schemas, CLI help, docs indexes and changelogs are generated in CI; contract changes show up as snapshot-test diffs | no conflicts on generated files |
| 5 | **Append-only, uniquely named files** for migrations (`2026-10-11T1200_add_face_profile.rs`) and changelog entries (one file per PR in `.changes/`) | two PRs never edit the same line |
| 6 | **A mock for every API:** headless renderer (software GPU), fake tracker (replays a recorded track), fake platform events, fake connectors, fake clock | every PR builds and tests on any machine without cameras, GPUs, accounts or network |
| 7 | **Walking skeleton first.** The end-to-end path (input → retarget → face → render → output, plus op → MCP) exists early with stub implementations; parallel work replaces stubs one at a time | nobody waits for someone else's subsystem to exist |
| 8 | **Feature flags + trunk-based development.** Unfinished work merges dark behind cargo features or runtime flags; branches live hours to days, not weeks | no long-lived branches to reconcile |
| 9 | **Deterministic, reproducible checks.** Golden renders, recorded inputs and seeded RNG; `cargo xtask check --affected` runs exactly what CI runs | a contributor, human or agent, can prove a PR is green before opening it |
| 10 | **Enforced boundaries.** A layering check (`xtask lint-deps`): impl crates may depend only on `*-api` crates, `omuzaki-core` and shared format libraries (`layer = "lib"`, ADR 0011). Plus cargo-deny bans and public-API snapshot tests (`cargo public-api`) on API crates | accidental coupling fails CI instead of causing conflicts later |
| 11 | **Workspace globs.** `members = ["crates/*"]`; dependency versions centralised once in `[workspace.dependencies]` and rarely touched | adding a crate doesn't edit shared lines |
| 12 | **Per-crate ownership** in `.github/CODEOWNERS`; API crates need a maintainer's review | clear reviewer for every file; API stability |

**API crates (phase 1):**
- `omuzaki-core`
- `omuzaki-ops-api`
- `omuzaki-doc-api`
- `omuzaki-render-api`
- `omuzaki-char-api`
- `omuzaki-face-api`
- `omuzaki-anim-api`
- `omuzaki-track-api`
- `omuzaki-audio-api`
- `omuzaki-stream-api`
- `omuzaki-live-api`
- `omuzaki-ai-api`
- `omuzaki-io-api`
- `omuzaki-plugin-api` (WIT)

Each comes with a mock implementation crate (`*-mock`).

### 39.2 Workflow

1. **Backlog from feature IDs.** Every feature ID (§12–§16, §17–§31 and §34) is an epic. It's split into **tasks of at most about a day or 400 changed lines**. Each task issue states:
   - goal
   - **fence** (crates and folders it may touch)
   - contracts it uses
   - fixtures
   - acceptance commands
   - expected images or numbers
   - what's out of scope
2. **Ready only when unblocked.** A task is `ready` only when the APIs it needs exist (mocks count). Maintainers keep the task dependency graph and mark tasks `ready` as their blockers close.
3. **Isolation.** Each contributor (person or agent) uses their own branch and git worktree. AI agents always run in worktree isolation.
4. **Proof in the PR.** CI posts:
   - golden-render diffs as images
   - perf deltas vs budgets
   - the licence report
   - the API snapshot diff, if any
   - MCP schema changes

   Reviewers approve outcomes they can see.
5. **Review:**
   - **automated review:** an automated review checks scope, the fence and the gates, for PRs inside one impl crate with green gates and no API, UX or art changes.
   - **maintainer review:** API crates, UX, art direction, security, licences and new dependencies.
6. **Merge as soon as gates are green,** so PRs land continuously. Maintainers may merge in batches. Cargo.lock conflicts are resolved by rebasing and regenerating, never by hand.
7. **Fast CI:**
   - affected-crate detection, cargo-nextest and a shared compile cache (sccache)
   - target **< 10 min** for a PR
   - golden renders on the software renderer in every PR; GPU-only golden tests on a dedicated GPU runner through a queue
   - full matrix (Windows, macOS, Linux, WASM) nightly
8. **Contracts change deliberately.** Breaking API changes need an ADR, a version bump, and a migration PR that updates all implementers (often fanned out as parallel tasks).
9. **Docs and changelog by construction.** Op docs come from schemas; `.changes/<pr>.md` files are compiled at release.
10. **Capacity.**
    - phase 1: about 10 parallel streams (one per API/impl pair)
    - phases 2–3: 20–40 parallel tasks (trackers, exporters, ops, library items, automation nodes, gates are all independent files)
    - the library and op catalogue scale to hundreds of small parallel PRs

**Dog-fooding.** The same mechanics (fences, branches, gates, the Build Theatre) are what users' agents use inside the product (§12–§13). How we build Omuzaki is the product's own workflow.

### 39.3 The three standards

**Three standards every PR must meet (non-negotiable):**
1. **Good engineering.** DRY; clear module boundaries; small focused functions; meaningful names; comments that explain *why*; docs on every public API; tests with every change; no dead code.
2. **Performance.** Within the §10 budgets; no allocation or locking in real-time hot loops; before/after numbers for any real-time-path change; criterion benchmarks for hot code, tracked in CI.
3. **Quality and correctness.** Correct first; unit + golden-render + property tests where useful; explicit error handling (no `unwrap`/`expect` in library crates); deterministic; evidence attached.

**Enforced in CI:**
- rustfmt; clippy `-D warnings` plus a curated pedantic set; `#![deny(missing_docs)]` on API crates; `clippy::unwrap_used` / `expect_used` denied in library crates
- cargo-deny (licences, bans, sources)
- golden renders; perf budgets; benchmark regression alerts
- the public-API snapshot check

Whatever CI can't check (design quality, taste, UX), maintainers check in review.

## 40. Licensing

> Restored/added 2026-10-11 (decision: no later tier): the OBS plugin ships as a separate GPL project, and Live2D Cubism is recorded as not used.

**Project rule: nothing non-commercial, ever,** in the product or in the pipeline that builds it. That covers libraries, tools, models (with their training data), datasets, assets and service outputs.
- **Policy:** `docs/licensing/policy.md`
- **What we use, with verdicts:** `docs/licensing/register.md`
- **Evidence:** `docs/research/2026-10-licence-audit.md`

### 40.1 The rules in brief

| Verdict | Examples |
|---|---|
| **Allowed** | MIT, Apache-2.0, BSD, ISC, Zlib, Unlicense, CC0; MPL-2.0 (unmodified); OFL fonts; CC BY assets with attribution |
| **Allowed with conditions** | LGPL native libraries as shared libraries (FFmpeg, librtmp); OpenRAIL model licences (use restrictions flow to users); NDI, NVIDIA and DirectML runtimes under their redistribution terms |
| **External only** | GPL tools as separate programs: Blender, ComfyUI, v4l2loopback. Scripts that import `bpy` stay internal. |
| **Banned** | non-commercial or research-only terms; models trained on non-commercial data; GPL/AGPL linked into the product; SSPL / BUSL / Commons Clause; service outputs the vendor owns; third-party IP or likeness in anything shippable |
| **Unverified** | treated as banned until a primary source or legal review clears it |

### 40.2 What the audit changed in this spec

| Area | Before | Now |
|---|---|---|
| Speech (`omuzaki-audio`) | sherpa-onnx for ASR, TTS and VAD | Whisper + Silero VAD; Kokoro/Chatterbox weights through our own inference |
| Image generation | Flux / SDXL | FLUX.1 [schnell] (Apache-2.0); SDXL with its use restrictions; never FLUX.1 [dev] |
| 3D generation | Meshy, Tripo, TRELLIS | Meshy and Tripo on paid plans only; TRELLIS only through a proven geometry-only path |
| OBS plugin (BR-03) | a closed plugin in `omuzaki-stream` | ships as a separate GPL-licensed plugin over IPC (decision 2026-10-11); legal review reviews the boundary |
| Live2D Cubism | "keep Live2D import" (v2), then dropped without a record | not used: approval-gated Publication License for VTuber apps; flat 2D through Inochi2D instead (EX-08, decision 0010) |
| Encoding | FFmpeg | LGPL FFmpeg as shared libraries + hardware encoders; one of FFmpeg or GStreamer |
| Webcam tracking | MediaPipe weights licence unknown | Apache-2.0 per the model cards; self-host and pin |
| Own tracker data | ICT-FaceKit renders | only after USC ICT clears commercial use; fallback FLAME 2023 Open + own captures |

### 40.3 Enforcement

- **Every PR:** `cargo deny check` with `deny.toml`. It enforces:
  - a permissive allow list, so anything else fails
  - bans on `sherpa-onnx`, `asio-sys`, `intel-mkl-src` and `openssl-src`
  - crates.io as the only source
- **Repo licence gate:** register check, banned-item check, third-party notices generated for releases.
- **Product licence gate (§7, §15):** `publish` is blocked for anything `no` or `unknown`.
